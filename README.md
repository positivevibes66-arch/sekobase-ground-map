## pile.html — 杭の傾斜・偏芯計測

打設中の杭の傾斜をスマートフォンのカメラで計測し、偏芯の実測値と組み合わせて
**設計杭頭レベル（地中）での偏芯**を求める。外部機材は不要。

### 計測の原理

スマホを鉛直に構える（＝光軸を水平にする）と画像面が鉛直になり、
**世界の鉛直線は画面上でも必ず鉛直線に写る**（透視投影の性質）。
したがって画面上で「重力から求めた真の鉛直方向」と「杭のエッジ」がなす角が、
そのまま実際の傾斜（撮影方向に直交する成分）になる。
直交する2視点から測れば傾斜ベクトルが決まる。

- **方位磁石を使わない。** 鉛直の基準は重力のみなので、鋼管杭の近傍でも磁気の影響を受けない。
- **カメラのロール（傾け持ち）は補正される。** 重力ベクトルを基準線にしているため。
- **回転を止める必要がない。** 円筒のシルエットは回転しても変わらない。
  むしろ首振り（偏心回転）が疑われる場合は複数回撮って平均する方が正確。

### 連続計測（既定）とその理由

回転圧入では杭が首を振る（偏心回転する）ことがあり、**静止画1枚では振れのピークを
掴んでしまう**。1回転分を通して平均すれば首振り成分が消え、回転軸そのものの傾斜が残る。

そのため既定は **連続計測**：ガイド線を杭の左右の縁に合わせて開始すると、
指定秒数のあいだ毎フレームを解析し、平均・ばらつき(1σ)・時系列を記録する。

**動画ファイルは作らない。** `MediaRecorder` で録画すると、フレームのタイムスタンプと
センサー値を後から突き合わせる必要があり、ブラウザでは信頼できる同期が取れないため。
代わりに `requestVideoFrameCallback` でライブのフレームを1枚ずつ取り出し、
その場で「そのフレームの重力ベクトル」と対にして解析する。
操作性は動画と同じまま、同期の問題が消える。

- エッジは**輝度勾配のピークを放物線フィットでサブピクセル**まで求める。
  走査線ごとに候補を複数残し、**RANSAC で最も多くの走査線が乗る1本の直線**を選ぶ
  （文字や陰影など、輪郭と紛らわしい線に引きずられないため）。
- 走査する縦方向の範囲は、指定された4点の上下端から決まる。
- 初回フレームで杭が背景より暗いか明るいかを判定し、エッジの極性を決める。
- ピッチが許容外のフレーム、追跡に失敗したフレームは自動で除外される。
- 検出できない場合は**誤答せず棄却**する（`test/edge-tracking.test.js` で確認）。
- 傾斜の時系列がそのまま**首振りの波形**として残る。

### 動画ファイルからの計測（据置きカメラ）

各視点の「動画」ボタンから、ネットワークカメラ等で撮った映像を読み込んで解析できる。

固定カメラには IMU が無いが、**カメラが動かないので鉛直の基準はクリップ全体で1回
決めれば足りる**。下げ振り・水準器で立てたポール・建物の柱など鉛直と分かる物を
画角に入れておき、その1本を2点で指定する（水平に据えたことが確かなら画像の鉛直をそのまま使う）。

手順は ① 鉛直基準 → ② 杭のエッジ（追跡の初期値）→ ③ 解析。
解析速度は 1〜8倍から選ぶ。早送りするとブラウザがフレームを落として採用点数が減るが、
落ち方はランダムなので平均は歪まない（`test/video-e2e.test.js` で確認）。

> **1台しか据えられない場合**、得られるのは**視線に直交する1成分だけ**で、合成傾斜は求まらない。
> 単眼である限りこれは原理的な限界で、回避策はない（奥行き方向の傾きは単眼では精度が出ない）。
> したがって据置き1台は**トレンド監視**（ズレ始めの検知）に使い、
> **2軸の確定値はスマホの直交2視点**で取る、という分担になる。
> カメラは通り芯に平行に据えると、測れる成分が偏芯の実測と同じ座標系になる。

### 実映像で分かったこと

実際の打設映像（羽根付き鋼管杭 φ318.5×10.3 STK490 / 回転圧入 / 4K・24fps・手持ち）で
検証した結果、合成データでは見えなかった破綻が3つ出た。いずれも修正済み。

**① 走査範囲を画面比で固定していた** — 実際の杭は画面の上半分にしか写っておらず、
下半分では地面のテクスチャを追いに行って **116フレーム中0フレーム**しか通らなかった。
指定した4点の上下端から走査範囲を決めるようにして解決。

**② 走査線ごとに独立して「最も強い勾配」を選んでいた** — 杭に書かれた製品表示の白文字や、
円筒の陰影が作る輪郭と平行な線のほうが強く、そちらを掴んで直線に乗らなかった
（検出自体は毎フレーム11/11成功しているのに残差が中央値2.8〜7.1px）。
候補を残したまま **RANSAC で「最も多くの走査線が乗る1本」を選ぶ**方式に変更。
残差 1.05px → **0.42px**。

**③ 左右両方のエッジが揃うことを条件にしていた** — 杭の片側が重機のリーダーに重なると
その側の輪郭は候補にすら挙がらず、良く写っている側まで巻き添えで捨てていた。
角度を測るのに必要なのは軸に平行な直線が1本あることだけなので、
**通ったほうを使う**（両方通れば平均し、食い違いが大きければ棄却）。

**④ 左右のエッジの角度が食い違うフレームを棄却していた** — 杭のそばには重機のリーダーなど
別の鉛直な線があり、片側がそれを掴むと食い違う。棄却すると、良く写っている側が
毎フレーム通っているのに 57/116 が落ちていた。棄却せず、**当たりの良いほう**
（乗った本数 → 残差 → 指定位置への近さ）を採り、食い違い量は記録する。

**修正後の追跡率は 116/116（100%）**、直線フィットの残差 0.42px。

### カメラのロールは平行移動には現れない

同じ映像で背景の動きを実測したところ、**平行移動は最大18px（4K幅3840pxの0.5%）**
しかなかった。手持ちでもカメラはほとんど動いていない。
ところが**光軸まわりの回転（ロール）は 0.78°** あった。ロールは平行移動として現れないので
見落としやすいが、**管理値 1/100 = 0.573° より大きい**。

そこで動画ファイルからの計測では、指定された鉛直基準を**毎フレーム追跡**して
その向きを重力の代わりに使う。実映像で検証した効果:

| | 杭の角度のばらつき (1σ) |
|---|---|
| 補正なし | 0.512° |
| 鉛直基準を毎フレーム追跡 | **0.328°** |

追跡した基準の回転量（0.72°）は、背景全体の回転を独立に推定した値（0.78°）と一致した。

補正後に残る 0.328° は杭自身の動き（風・圧入中の揺れ）と考えられる。
**1回の静止画では管理値の半分以上ずれうる**ということで、連続計測して平均する意味がここにある。

> 鉛直基準を指定しない場合は画像の鉛直がそのまま使われる。据置きカメラならそれでよいが、
> **手持ち映像では必ず①で鉛直基準を指定すること。** 下げ振り・電柱・建物の柱など、
> 画角内に鉛直と分かる物が写っていればよい。

### 偏芯監視システム — 機材と据え方

**基準を画角に入れるかどうかで、三脚に必要な安定度が3桁変わる。**

杭径 φ406.4 を距離10mで4K撮影した場合のスケールは 3.32mm/px、許容100mmは 30px。
このとき**カメラのヨーが 0.057° ずれるだけで 10mm の誤差**になる。
三脚の脚が1m離れているとして、1本が **1mm 沈めば使い切る**量である。
軟弱地盤で、横で杭打機が動いていて、杭芯セットから完了まで20分――という条件では保てない。

そこで**逃げ棒（画角内の動かない鉛直物）を一緒に写し、杭の位置をそこからの相対で測る**。
毎フレーム基準を追い、開始時からの差を偏芯とする。カメラの動きは両方に等しく効くので打ち消される。

| 基準の置き方 | カメラが20mm動いたときの誤差 |
|---|---|
| 基準なし（絶対座標） | 約250mm |
| 逃げ棒が3m手前 | 8.6mm |
| 逃げ棒が1.5m手前 | 3.5mm |
| **逃げ棒が杭と同じ距離** | **0mm** |

→ **カメラから見て逃げ棒と杭が同じくらいの距離になる位置に据える。**
測りたい通り芯に直交する方向から見れば、その通り芯上の逃げ棒は杭の真横に並び、距離が揃う。

`test/video-e2e.test.js` で、三脚が125mm相当ドリフトする合成映像から
杭の移動80mmを誤差0mmで復元できることを確認している。

#### スマホ

解像度は効かない。1080pでも 6.6mm/px（許容100mmの1/15）で足りる。効くのは別の要素:

- **熱**。4K30を20〜30分は夏場に止まる。**1080pで撮る**のが実用的（発熱も容量も1/4）。日陰に置くか白布をかける
- **電池と容量**。4K30 で約350MB/分・30分で12GB。1080pなら3GB
- **レンズは標準（1×）**。超広角は歪みが大きい。デジタルズームは使わない。光学望遠があればむしろ有利
- **AF/AEを固定する。** ピントが動くと焦点距離がわずかに変わり（フォーカスブリージング）、mm/px が揺れて偏芯に直接効く。
  純正カメラアプリなら長押しでAE/AFロック。アプリのライブ計測では対応機種で自動的に固定を試みる
- **手ブレ補正（OIS/EIS）は本来オフが望ましい**。特にEISは画面を歪ませる。ただし基準との相対で測れば、
  画面全体に等しくかかる分は打ち消されるので、致命的にはならない
- 新しい高性能機より、**熱に強い機種・大容量電池・現場に置きっぱなしにできる安い機体**のほうが向く

#### 三脚

相対測定にすれば要求は「倒れない・画角から外れない」程度まで落ちるが、それでも:

- **測量用三脚（スパイク付き）が本命**。写真用のゴム脚は軟弱地盤で沈む・滑る
- 写真用を使うならスパイク脚に替え、**各脚の下に敷板**（コンパネ端材で十分）
- **低く広く**。センターポールは伸ばさない（一番たわむ）
- 脚を踏んでスパイクを効かせてから撮り始める
- **重り**（土嚢・水袋）をセンターに吊るす。風で振れないよう地面に触れる程度に
- スマホホルダーはバネ式より**ネジで締める金属クランプ**。バネはガタが出る

### 偏芯を映像から測る

**杭径が既知なら、杭の見かけの幅がそのまま mm/px のスケールになる。**
実映像（φ318.5mm が 129.6px）では 2.457 mm/px、サブピクセル 0.3px は 0.74mm。
偏芯の許容 min(D/4, 100) = 79.6mm は 32px に相当するので、**分解能は桁で足りている**。

手順に「③ 設計芯」を追加した。逃げ杭からの水糸の交点や地面のマークを1点で指定すると、
杭の中心線をその高さで評価して差を mm で出す。

**カメラの動きを補正する必要がない。** 同じ画面の中で「杭の中心線」と「設計芯」の
距離を測る相対量なので、カメラが動いても両方が同じだけ動いて打ち消される。
（背景を基準にカメラの動きを引く方法は、背景と杭で奥行きが違うため視差で成立しない。
実映像で相関を見ると +0.11 しかなかった。）

合成映像での検証: 真値 100.0mm に対して **104.1mm**（誤差 4.1mm ≒ 0.8px）。

制約:

- **1台のカメラでは1成分だけ。** 傾斜と同じで、視線に直交する方向しか測れない。
- **設計芯と杭は同じくらいの奥行きにあること。** 10m先で1m奥行きが違うとスケールが10%ずれる。
- **同じ画面の高さで比べること。** 高さが違うと視差が乗る（設計芯の指定点の高さで杭の中心線を
  評価しているので、地面のマークを指定すれば自動的に揃う）。
- スケールに使う見かけの幅は、追跡値のばらつきが小さいときだけ追跡値を使い、
  そうでなければ**②で人が指定した左右エッジの間隔**を使う。実映像では片側が重機を
  掴むフレームがあり、追跡した幅が中央値130pxに対して振れ幅48pxになった。

### 精度と制約

| 項目 | 値 |
|---|---|
| 単発（1枚）の再現性 | 画像ノイズ ±10階調で 1σ=0.008°、±35階調でも 1σ=0.030° |
| 連続計測 | 誤差は系統的な偏りを持たない（40枚平均の偏り ≦0.007°）ため、平均で落ちる |
| 首振りの影響 | 振幅±0.25°の首振りに対し、単発は最悪0.25°ずれる。60フレーム平均で0.001°以下 |
| 追跡できる傾斜 | 1/7（8°）まで復元を確認。許容超過の杭でこそ失敗しないこと |
| 撮影ピッチ許容 | 既定 ±1.0°（超えるとシャッターが切れない） |
| 遠近誤差 | 杭を画面中央±15%に収めれば 0.1° 未満（`test/measure-math.test.js` で検証済み） |

- 杭全体を画面に入れる必要はない。まっすぐな一部分が長く写っていれば十分。
  上に向けて撮ると鉛直線が収束して誤差が出る。
- **縦持ち専用。** 横向きにすると画像座標と端末座標の対応が崩れる。
- カメラとセンサーの利用には **HTTPS** が必要（GitHub Pages 可）。

### 傾斜センサーからの入力

1台のカメラでは視線に直交する1成分しか測れず、XYを揃えるには視点を90°変える必要がある。
**2軸の傾斜センサーを杭に付ければXYが一度に出る**ので、この壁が無くなる。

機種ごとに通信仕様が違うため、まず**読んだ値を入れる経路**を用意している
（表示だけのセンサーでも、BLE付きでも同じように使える）。単位は度と mm/m のどちらでも入る。
センサーで入力すると、軸の呼び方が「視点A/B」から「X方向/Y方向」に切り替わり、偏芯の入力も同じ軸で揃う。

センサー選定の目安:

- 管理値 1/100 = 0.573° に対して **±0.1°級**が欲しい（ADXL345系の安価なボードは±0.5°級で足りない）
- **買ったら必ず自分で検証する。** 既知の傾斜（1mで10mm）を作って測る
- 温度ドリフトが効く（0.005°/℃なら30℃で0.15°）
- **回転圧入なら自己校正できる。** センサーが杭と一緒に回るので、1回転ぶんのXY出力は円を描く。
  円の半径が真の傾斜、円の中心がゼロ点誤差＋遠心力。ゼロ点も温度ドリフトも遠心力も同時に抜ける
  （遠心力は5rpm・半径0.16mで0.25°相当あるので無視できない）
- 回転する杭に付けるので、マグネットだけでは飛ぶ。クランプ＋落下防止ワイヤーが要る

### 計測ステップ

`杭芯セット` → `建込み` → `圧入中` → `溶接前` → `溶接後` → `最終`

**杭芯セットが偏芯の原点になる。**

現場では逃げ棒2本からテープを張って 0.0 に合わせる。だから:

1. 杭芯セットで、逃げ棒2本の**読みをそのまま記録**する（設計距離は要らない）
2. 最終計測で、**同じ測り方**で読み直す
3. **読みの差がそのまま偏芯**

設計芯を画像で認識する必要も、地面のホモグラフィ（4点必要、逃げ棒2本では組めない）も要らない。
符号は「逃げ棒から遠ざかる向きが＋」。

逃げ棒の呼び名と2本の成す角は設定タブで決める。**直交していなくても正しく合成する**
（テープの伸縮量は2方向への射影なので、成す角が分かれば元のベクトルが復元できる）。
偏芯の実測が無い場合や別の測り方をした場合のために、ズレ量を直接入れる経路も残してある。

> 100mm程度の移動なら、テープの読みの変化は移動量のその方向への射影とみなしてよい。
> 距離1.5mで100mm直交方向に動いても読みは3.3mmしか変わらないので、この近似で問題ない。

- **溶接前後**の傾斜ベクトルの差から、**継手の折れ角**が算出される。
  下杭が真っ直ぐでも継手で折れれば先端は大きくずれ、段数分だけ累積する。
- **最終**ステップで偏芯の実測値（逃げ杭・通り芯からのズレ）を、
  傾斜と同じ2方向・同じ符号（その視点から見て右が＋）で入力する。

### 設計杭頭レベルへの外挿

```
e_head = e_meas − t × Δh          Δh = 偏芯計測高さ(GL+) + 設計杭頭深さ(GL−)
```

杭軸は上へ行くほど +t だけ水平にずれるため、下がる分の符号は負になる。

判定は `合成偏芯 ≦ min(D/4, 上限値)`（上限の既定は 100mm、設定で変更可）。

> **前提** 外挿は杭が直線であることを仮定している。地中での偏向（玉石・支持層の傾斜など）は
> 地上からは判定できない。ヤットコ使用時は「ヤットコと杭が同軸」という前提で扱われ、
> その旨が判定結果に明示される。

### IFC 書き出し（BIM連携）

杭1本を完全に記述するには2つの軸の記録が要る。

| | 記録する軸 |
|---|---|
| 杭打機搭載の施工管理装置（セコーマスター等） | **Z方向・地中** — 深度、トルク／押込力、支持層到達 |
| このアプリ | **XY方向・地上** — 偏芯、傾斜 |
| **IFC の `IfcPile`** | **その合流点** |

記録タブの「IFCを書き出す」で IFC4 のファイルが出る。`IfcPile` に3つのプロパティセットが付く。

- `Pset_PileCommon` — Reference（杭番号）, Status, LoadBearing
- `Pset_SEKOBASE_PileSpec` — 工法, 鋼種, 杭径, 肉厚, 杭長, 設計杭頭深さ, ヤットコ
- `Pset_SEKOBASE_PileAsBuilt` — 基準軸, 杭芯セットの読み, 偏芯（各軸／杭頭／合成）, 許容, 判定,
  外挿距離, 傾斜（各軸／合成／管理値）, 判定, 継手折れ角, 計測方法, 計測日時

形状は `IfcCircleHollowProfileDef` の押し出しなので、**鋼管の外径と肉厚がそのまま断面**になる。
設計座標を入れておけば正しい位置に立つ（無ければ並べて配置する）。

**設計モデルと突き合わせる鍵は杭番号。** `Name` / `Tag` / `Pset_PileCommon.Reference` の3か所に
同じ値を入れてあるので、上流のモデル側がどれを使っていても当たる。
表記ゆれ（`No.12` / `P-12` / `12`）が統合の最大のリスクなので、**モデルと同じ表記で登録すること**。

GUID は杭ごとに固定して台帳に持たせる。書き出すたびに変わると上流と結び直せなくなるため。

> プロパティだけを書き戻す経路のほうが本来は望ましい（未実装）。

### 検証

```
node test/measure-math.test.js     # 幾何の数式
node test/edge-tracking.test.js    # エッジ追跡
node test/video-e2e.test.js        # 動画解析（要 npm i playwright-core、無ければスキップ）
node test/sensor-flow.test.js     # センサー入力〜偏芯判定（同上）
node test/ifc-export.test.js      # IFC書き出し（要 ifcopenshell、無ければスキップ）
```

前2つは `pile.html` から該当部分を取り出して実行するので、式が二重管理にならない。

**`measure-math`** — 既知の傾斜を持つ杭を既知の姿勢のカメラで透視投影した合成データで、
重力ベクトルの導出、カメラロールに対する不変性、2視点合成、遠近誤差の上限、
外挿の符号、継手折れ角、許容値を確認する。

**`edge-tracking`** — 既知の傾きの杭の合成画像（ぼけ・ノイズ入り）で、
サブピクセルのエッジ検出と直線フィットを確認する。
明暗どちらの背景でも、カメラを傾け持ちしても、ガイド線が40pxずれていても復元でき、
コントラスト不足のときは誤答せず棄却すること、
縁のすぐ内側に白文字と陰影の線があっても惑わされないこと、
**カメラのロールを画角内の鉛直基準で打ち消せること**（1σ 0.610° → 0.004°）、
そして首振りが連続計測の平均で消えることを検証する。

**`sensor-flow`** — 傾斜センサーの数値入力 → 杭芯セットを原点にした偏芯 → 設計杭頭への外挿 →
許容判定 までを実際の操作経路で辿る。φ406.4・設計杭頭GL-1.0m・逃げ棒の読み 1500/1200 → 1535/1180
（＝ズレ +35/-20mm）・傾斜0.45/0.30°で、合成偏芯 36.3mm が手計算と一致することを確認する。

**`ifc-export`** — 書き出した IFC を **ifcopenshell で読み直して**、実体・空間構造・単位・
断面形状・世界座標での配置・形状生成・日本語プロパティの往復・判定値までを確認する。
ビューアや BIM ソフトが読める形かを、実際のパーサで確かめている。

**`video-e2e`** — 合成した杭の映像をブラウザ内で canvas → MediaRecorder で作り
（VP8圧縮を通すので実際のカメラ映像に近い劣化が入る）、
ファイル選択 → エッジ指定 → 解析 → 保存 という実際の操作経路をそのまま辿る。
640×480・圧縮あり・首振り振幅±0.3° の条件で、真値0.42° を誤差0.03° 以内で復元することを確認する。
